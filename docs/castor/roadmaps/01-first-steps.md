# 1 — First steps

[Overall roadmap](../roadmap.md) · Next: [first play](02-first-play.md)

**Goal:** choose the tools through a small experiment and be able to run a scene outside the editor. Prerequisite: no game code.

Detailed execution: [startup plan](../startup-plan.md). It also includes importing a first simple 3D object and organizing the art sources.

Current status: Godot chosen and set up, cube exported and movement/collisions tested on Windows. Phone unavailable, with continuing on the PC authorized. Asset import and running on Android remain pending; the milestone is not complete.

## Learning while building

| Concept | Application in Castor |
|---|---|
| Scene and objects | Bring together ground, provisional beaver, light and camera. |
| 3D coordinates and transforms | Position, rotate and scale the objects. |
| Per-frame update and elapsed time | Move the beaver without tying speed to the frame rate. |
| Collisions | Prevent it from passing through the ground and the valley's limits. |
| Export | Run on the PC and install on Android without the editor. |

## Tasks

- [x] Identify the PC's operating system, the phone's Android model/version and how to connect the device for testing.
- [x] Compare Godot/GDScript, Godot/C# and Unity/C#, according to the startup plan. Consult current official documentation on export, support for the chosen language, requirements and licenses. C# is a possible advantage, not an obligation. Only dig deeper into packaged Three.js if there is a concrete reason.
- [x] Choose a candidate engine and a language for the experiment: standard Godot 4.7.2 and GDScript, according to the technical decisions.
- [x] Before setup, define an effort limit for investigating export failures; when it is reached, record the problem and reassess engine/language according to the startup plan.
- [x] Install the necessary tools and create an experiment project separate from the documents.
- [x] Set up version control and ignore the files generated by the engine before work piles up.
- [x] First export a minimal scene with a cube rotating as a function of time and open it outside the editor, isolating export from movement problems.
- [x] Create ground, light, tilted camera and a capsule or simple shapes for the beaver.
- [x] Make the beaver move with a provisional control, respecting the ground and the limits.
- [x] Build and open a version on the PC.
- [x] Build and install a version on Android. Check image, basic input and running outside the editor; this is not yet an assessment of the final controls.
- [ ] Record engine and version, language, export steps, difficulties and the decision to continue or switch. Version, steps and difficulties recorded; the explicit decision to keep or switch is missing (task 4 of the startup plan).
- [x] Create or adapt a simple branch in a 3D tool and check export, import and update in the engine, according to the [production inventory](../3d-production.md).
- [x] Also import a test model with a skeleton, idle and walk, with a verified license; switch animations in the installed build according to the startup plan.

## Completion criterion

The scene opens on both real devices and basic movement works. Importing a static asset and an animated model has been tested. There are enough instructions to repeat the export and an explicit engine choice. The choice of the MVP device can still wait for milestone 2.

If the export fails, resolve that uncertainty before producing content. If a platform needs to be postponed, record that decision with you and the risk left pending.

**Not needed now:** final models, final animations, dam, player inventory system, complete courses or an extensible architecture for several games. The animated test model and the production asset log are part of this milestone.
